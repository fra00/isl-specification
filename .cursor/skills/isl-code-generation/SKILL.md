# ISL code generation (in-agent compiler)

## Hard constraints

1. **Do not run the ISL Compiler toolchain** for code emission:
   - No `isl-generator`, no Node entrypoints that wrap it, no npm/yarn scripts whose purpose is “compile ISL → bin”.
   - Do not instruct the user to run those commands as a substitute for your work unless they explicitly ask only for the tool.
2. **You are the compiler**: Perform the same *logical* job as `tools/vscode-isl/src/isl-generator` (context assembly → single-file code → write under `bin/`), using your reasoning and file tools—not an external LLM client invoked by that package.

## What “compile” means (non-negotiable)

- **Compilation / generation** = changes in **ISL** (signature, capability, content, constraints) must show up in the **artifact source** under `bin/` (and `*.sign.ts` when used).
- **Only verifying that a file exists in `bin/`** and then **bumping `gen-lock.json` to manifest hashes** is **not** compilation: it aligns *metadata* without aligning *implementation*. **Do not** use that as a substitute for real work. The lock exists to *record* that the build context was already translated into coherent code—**after** that coherence exists.
- If the lock was updated without code truly reflecting the ISL, the queue looks falsely empty. **Deleting `build/gen-lock.json`** restores an honest queue (hash mismatches for units with `implementationPath` until you fix the lock after updating code).
- When the queue lists a unit, **minimum obligation**: compare `*.isl.md` (and the source section in `*.build.md`) with the file in `bin/`; if props, branches, exports, or behaviors required by capabilities are missing, **edit the code** (or explicitly tell the user what is missing and why).

## What “same as isl-generator” means (mirror `StandardRunner`)

1. **Resolve target path**
   - From the ISL frontmatter / `**Implementation**` header, compute the output path under `example/dungeon/bin/` (or the stack’s `bin` root).
   - Match file extension to **Role** and project conventions (e.g. Presentation → `.jsx` for the dungeon React stack), consistent with existing siblings.

2. **Load compile context** (prefer richest available)
   - Prefer **`isl-builder`** first when contexts are missing or stale (see below): it writes `build/build-manifest.json`, per-file `.build.md`, and `.ref.md` under the stack’s `build/` folder.
   - Then read the relevant `*.build.md` as the full **Build Context** (`SOURCE FILE TO IMPLEMENT` + dependency interfaces).
   - If you cannot run the builder, fall back to the component `*.isl.md` and follow `> **Reference**:` until imports and data shapes are clear.

3. **Dependency reality (dynamic linking)**
   - Before importing from other modules under `bin/`, read those files (and `*.sign.ts` if present) so exports and names match **what actually exists**, not guesses from prose.
   - Treat that as the override described in `tools/vscode-isl/src/isl-generator/prompts.ts`: execution contracts come from real code; data shapes still align with ISL/ref where relevant.

4. **Emit artifacts**
   - Write **one implementation file** per component (full implementation, no mocks), standard warning header:

```text
/**
 * DO NOT EDIT THIS FILE DIRECTLY
 * ----------------------------------
 * This file was generated by ISL Compiler.
 * Source: <basename-of-.isl.md>
 * Edit the ISL file instead.
 */
```

   - If the stack expects a sibling signature file (`*.sign.ts`), write or update it when imports/types must feed downstream compiles.

5. **Multipart `#[CODE]` blocks** are for the external LLM pipeline only—you write files directly. **`gen-lock.json`**: update **only** with `llm-tools/run-update-gen-lock.cjs` **per build file** **after** the artifact in `bin/` has actually been brought in line with the ISL. **Do not** use bulk lock sync as a shortcut to “clear” the queue without updating code.

## ISL source of truth

- **`*.isl.md`** defines contracts and behavior; **`bin/`** must reflect it after your edit.
- Normative references: `specs/Code Generation Protocol.md`, `specs/Intent Specification Language (ISL).md`.

## Allowed tool: ISL Builder (`isl-builder`)

- **May and should run** when you need an up-to-date build graph, `build/build-manifest.json`, or merged `.build.md` contexts (e.g. after changing `> **Reference**:` edges or before generating a complex component).
- **Not** the code generator: it does not write `bin/` implementation files.
- From repository root, typical invocation:

```bash
npx tsx tools/vscode-isl/src/isl-builder.ts example/dungeon
```

  Adjust the last argument to the stack directory that contains the `.isl.md` sources (see `README.md` / examples for other stacks).

- Output lands under `<stack>/build/` (manifest + `.build.md` / `.ref.md` paths per `ISLBuilder`).

## Incremental queue (`llm-tools/`)

Same skip logic as `StandardRunner`: manifest order; skip when `lock[buildFile] === hash` and target file exists in `bin/` (unless `--force`).

1. **Discover work**: `node llm-tools/run-compile-queue.cjs --root example/dungeon`  
   Wraps `tools/vscode-isl/src/cli/agent-compile-queue.ts` (`compile-plan.ts`). Optional: `--json`; `--all --json` for every manifest row.

2. **For each queued item**: read ISL + context and **update code** under `bin/` until it reflects required contracts and behavior—not only the header.

3. **Record success** (only after step 2): `node llm-tools/run-update-gen-lock.cjs --root example/dungeon --build-file "<absolute-path-to-.build.md>"` for that unit.

See `llm-tools/README.md`. Implementation lives under `tools/vscode-isl/` — **no duplicated hash/path logic** in `llm-tools/`.
